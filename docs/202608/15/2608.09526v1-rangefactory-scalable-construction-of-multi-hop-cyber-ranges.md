## 摘要
现实世界的网络攻击往往需要跨多个主机和网络段持续推进，这使得多跳网络靶场成为研究和提升LLM智能体维持完整攻击链能力的关键基础设施。先前的工作已扩展了孤立的漏洞任务，并从手动指定的漏洞语义中构建了多主机场景。然而，它们仍无法自动将日益增长的漏洞环境供给编排成端到端验证的多跳靶场。为此，我们提出了RangeFactory，一种自动化网络靶场编排框架，可从孤立的漏洞环境中大规模构建多跳网络靶场。RangeFactory将靶场构建表述为依赖解析问题：它从智能体针对真实漏洞的实际攻击中提取依赖信息，通过模板引导的编排解析已知依赖，并使用端到端的攻击执行来验证组合后出现的运行时依赖。利用RangeFactory，我们构建了涵盖287条不同攻击链的1,148个已验证靶场实例的RangeBench，并评估了前沿攻击智能体在攻击深度、网络规模和任务信息方面的表现。在攻破入口漏洞的运行中，仍有24.5%-47.0%未能完成剩余的攻路径，揭示了在建立初始立足点与完成多跳攻击之间存在巨大的持续攻破差距。RangeFactory还生成了一个包含5,541条带结果标注的多跳攻击轨迹的语料库，为攻击过程分析和未来智能体训练提供了执行数据。

## Abstract
Real-world cyberattacks often require sustained progress across multiple hosts and network segments, making multi-hop cyber ranges essential infrastructure for studying and improving LLM agents' ability to sustain complete attack chains. Prior work has scaled isolated vulnerability tasks and constructed multi-host scenarios from manually specified vulnerability semantics. However, they are still unable to automatically orchestrate the growing supply of vulnerability environments into end-to-end validated multi-hop ranges. To this end, we present RangeFactory, an automated cyber-range orchestration framework that constructs multi-hop cyber ranges at scale from isolated vulnerability environments. RangeFactory formulates range construction as dependency resolution: it extracts dependency information from agents' actual attacks against real vulnerabilities, resolves known dependencies through template-guided orchestration, and uses end-to-end attack execution to validate runtime dependencies that emerge after composition. Using RangeFactory, we construct RangeBench with 1,148 validated range instances spanning 287 distinct attack chains and evaluate frontier attack agents across attack depth, network scale, and task information. Among runs that compromise the entry vulnerability, 24.5-47.0% still fail to complete the remaining attack path, revealing a substantial sustained-compromise gap between establishing an initial foothold and completing a multi-hop attack. RangeFactory further produces a corpus of 5,541 outcome-annotated multi-hop attack trajectories, providing execution data for attack-process analysis and future agent training.

## 2. 方法论：核心思想、关键技术细节与流程

### 2.1 核心思想：将靶场构建视为依赖解析

- 两个关键依赖类型：
  - **能力依赖（capability dependency）**：前序攻击必须提供后序漏洞利用所需的能力，例如“文件读取”不能支撑“命令执行”；
  - **运行时依赖（runtime dependency）**：具体攻击过程在组合后的环境中是否仍然可行，例如网络策略阻止回连、目标主机缺少工具等。
- **三步流程**：
  1. **从真实攻击中提取依赖**；
  2. **通过模板引导编排解析已知依赖**；
  3. **通过端到端攻击执行验证组合后浮现的运行时依赖**。

### 2.2 CVE 能力原子（CVE Capability Atom）

- 每个 Atom 包含四个核心字段：
  - `exploit_access`：结构化利用前提（攻击向量、所需权限、服务协议/端口）；
  - `capability_grants`：经探针验证的利用后能力（采用固定本体，佐证主体和证据）；
  - `exploit_guide`：成功攻击流程及运行时需求（工具、材料、认证、回调要求）；
  - `poc_materials`：攻击流程引用的 PoC 工件。
- 能力本体包括：`execute_command`、`read_file`、`write_file`、`network_vantage`、`read_credential`、`authenticate` 六类。
- 只有 `verified` 级别的能力授予参与编排，Agent 推断或声明的能力不能作为硬事实。

### 2.3 三阶段多智能体工作流

- **阶段一：Atomization（原子化）**
  - **Exploiter**：在独立漏洞环境中执行攻击，验证成功后将攻击过程蒸馏为 `exploit_guide`；
  - **Explorer**：复用已建立的立足点，执行能力探针，将确认的能力写入 `capability_grants`。
- **阶段二：Orchestration（编排）**
  - **Generator**：将公开架构参考转化为参数化企业级网络模板（如 DMZ → 内部应用网络 → 数据网络）；
  - **Composer**：按攻击链顺序绑定 Atom，检查能力累积是否满足下一跳的 `exploit_access`，并执行静态运行时检查；不兼容组合在部署前被剪枝。
  - 形式化表达：前缀状态满足 Atom 的判断为 Σ |= P(a, s)；能力授予表示为 ⟨t, σ, p, e, r⟩；绑定后通过闭包规则派生能力（如命令执行 ⇒ 文件访问 + 网络视点）。
- **阶段三：Validation（验证）**
  - **Executor**：将各跳利用组织为端到端攻击，根据新立足点动态调整过程；
  - **Diagnoser**：区分“攻击执行失败”和“链条组合失败”，执行有界重试，并将组合不相容记录反馈给 Composer，用于后续编排。

### 2.4 算法流程（文字描述）

- **组合算法（Algorithm 1）**：按依赖拓扑序展开槽位，对每个槽位尝试所有未使用的 Atom，检查兼容性硬门限 `Compatible(s, a, Σ)`（要求已验证 Atom、服务匹配、前序槽已解析、能力/身份/凭证/网络来源满足、输出能力子集、静态运行时约束通过），通过后执行作用域绑定与闭包更新状态，递归填充后续槽位。
- **验证算法（Algorithm 2）**：部署后依次执行确定性检查（镜像物化、路由、服务就绪、攻击图排序、前驱连通性），然后验证 Guide 完整性，运行 Executor，最后由独立 verifier 按序检查隐藏目标。

## 6. 主要结论与发现

- **RangeFactory 可扩展构建多跳靶场**：从 239 个 Atom 和 20 个配置出发，自动化产生 1,840 个候选，最终得到 1,148 个通过端到端验证的靶场实例。
- **持续攻破差距显著存在**：
  - L2 信息下，模型端到端成功率从 GPT-5.6-Luna 的 23.5% 到 Kimi-K3 的 55.7% 不等；
  - 在已攻破入口漏洞的运行中，仅 53.0%–75.5% 能完成整条攻击链，即 **24.5%–47.0% 在初期立足后仍失败**。
- **任务信息的影响**：L0→L1 增益较小，L2 带来大幅提升；但即使最好模型在近半靶场上失败，说明信息增多不能消除持续执行难度。
- **网络规模的影响**：从 none 到 high 规模，端到端成功率下降 9.8–10.6 个百分点，但工具调用增加 51–74%、时间增加 71–84%，说明扩展网络主要增加的是探索成本而非最终成功率。
- **依赖引导与端到端验证均不可或缺**：随机绑定端到端有效率为 4.0%，完整编排提升至 60.0%；仅环境检查会多接受 70 个无端到端攻击见证的候选。
- **诊断反馈有效**：诊断引导重试恢复 31 个攻击（无引导仅恢复 14 个）；不相容记忆使后续批次冲突复发率从 21/24 降至 8/24。

## 7. 优点

- **自动化程度高**：除一次性数据筛选和模板参考选择外，CVE 绑定、部署、验证均无需每靶场人工标注。
- **以实际攻击为依赖来源**：通过真实执行和探针验证提取能力依赖，避免依赖 Agent 未验证推理或不完整的 CVE 元数据。
- **依赖引导 + 端到端验证互补**：在部署前剪枝已知冲突（过滤 92.3% 提议），部署后通过完整攻击执行捕捉组合引起的新冲突。
- **评估设计与数据价值兼备**：同一攻击链前缀上定义 1/2/3-hop 成功，使深度差异不受入口难度影响；同时输出带验证器里程碑标注的多跳轨迹语料，兼具评估与训练潜力。
- **统计透明性较好**：给出链分组的不确定性估计、验证者敏感性审计、审计通过率（行为保留 97.3%、Atom 注释一致 94.7%）等，自我披露较为充分。

## 8. 不足与局限

- **场景覆盖有限**：仅覆盖 CVE 为中心的**线性三层攻击链**、容器化企业风格网络，未覆盖 Windows 域、云 IAM、复杂分支/合并攻击图。
- **评估统计力度有限**：单次 rollout 无法刻画任务内随机性；模型间温度设置不一致；部分差距在保守区间下不显著。
- **验证者依赖**：接受/拒绝结果受固定验证协议影响，存在约 8% 假拒绝；被拒绝候选并未被证明无效，但评估基准的客观性仍受此偏差影响。
- **依赖解析语义偏轻**：能力本体仅 6 类，闭包规则简单；凭据、认证、复杂网络策略等未充分建模，导致部分运行时问题只能靠昂贵端到端执行暴露。
- **算力/成本披露不完整**：未提供 GPU 型号、数量或训练/推理算力总量，远程 API 调用和 worker-hour 折算难以复现整体成本。
- **数据发布受限**：Exploit Guide、PoC 和原始轨迹需安全审查后发布，可能影响可复现性。
