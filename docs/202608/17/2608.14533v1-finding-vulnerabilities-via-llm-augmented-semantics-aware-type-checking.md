## 摘要
传统的静态分析漏洞检测依赖于安全专家将不安全的编码模式编码为算法规则。然而，这种方法通常侧重于语法模式，而忽略了代码中更深层的语义信息，例如变量和函数名称的含义。随着软件系统变得越来越复杂，仅使用语法规则对漏洞进行建模变得越来越具有挑战性。在本文中，我们提出了一种语义感知的软件漏洞检测方法。我们提出了SETYPE，一种语义感知的类型系统，它仅基于自然语言中符号和表达式的含义，即可直接从源代码中派生。在SETYPE类型系统中，类型推断和检查均由大型语言模型（LLM）执行，类型检查失败则表明存在潜在漏洞。我们开发了原型PYSETYPE，以证明SETYPE在检测Python Web应用程序漏洞方面的可行性。我们在真实世界应用程序上的评估达到了87%的检测精确率和88%的检测准确率。使用PYSETYPE，我们识别出15个潜在的零日漏洞，其中9个已得到开发者确认。

## Abstract
Vulnerability detection via static analysis traditionally relies on security experts encoding insecure coding patterns into algorithmic rules. However, this approach often focuses on syntactic patterns and overlooks deeper semantic information in the code, such as the meanings of variable and function names. As software systems grow more complex, modeling vulnerabilities using only syntactic rules becomes increasingly challenging.   In this paper, we propose a semantics-aware approach to detecting software vulnerabilities. We present SETYPE, a semantics-aware type system that can be derived directly from source code based solely on the meanings of symbols and expressions in natural language. In the SETYPE type system, both type inference and checking are performed by Large Language Models (LLMs), and a failed type check indicates a potential vulnerability.   We prototype PYSETYPE to demonstrate the feasibility of SETYPE for detecting vulnerabilities in Python web applications. Our evaluation on real-world applications achieves 87% detection precision and 88% detection accuracy. Using PYSETYPE, we identified 15 potential zero-day vulnerabilities, nine of which were confirmed by developers.

## 1. 核心问题与研究动机

- **传统静态分析的瓶颈**：传统静态漏洞检测工具（如 CodeQL、Bandit、semgrep）依赖安全专家手工编写基于语法结构（AST、CFG、PDG）的规则来近似程序语义。这种方式面临两大挑战：
  - **知识库不完备**：工具必须理解每个函数的用途与安全含义（如 `os.path.join` 的路径拼接行为），而库与框架快速演进使得手工维护知识库难以跟上。例如 `pymupdf4llm.to_markdown` 这一每月安装量达数百万次的库，CodeQL 和 Bandit 均无法识别其读取文件的行为。
  - **脆弱模式难以全面建模**：必须同时识别各种绕过与缓解手段（如输入验证、白名单检查），否则要么漏报、要么误报。CodeQL 有近 500 条手写规则却仍漏掉大量实际漏洞。
- **核心问题**：如何让静态分析工具在**程序语义层直接运作**，而非依赖脆弱的语法近似，从而在保持精度的同时提高漏洞检出率？
- **核心洞察**：漏洞可被类比为**类型系统**中的类型不匹配——某操作期望接收"已净化"的类型，却实际收到了"用户可控"的类型。而变量与表达式的语义类型（如"来自用户的文件路径"）难以从语法结构推导，但可以通过自然语言含义来理解。

## 2. 方法论：SETYPE 类型系统与 PYSETYPE 实现

### 核心思想

- 提出 **SETYPE（Semantics-aware TYPE system）**——一种语义感知类型系统，其中：
  - 每个变量、表达式的类型是**自然语言描述的语义类型**（如"来自外部客户端的路径"），而非传统编程类型（`int`/`str`）；
  - 类型推断与检查均由 **LLM** 完成，从源码的非可执行上下文（变量名、注释、docstring）出发；
  - **类型检查失败 = 潜在漏洞**。

### 关键技术设计

- **混合架构（Option 3）**：在确定性、算法化的代码遍历（保证覆盖率）之上，让 LLM 在局部类型检查上下文中灵活推理（避免僵化规则）。与"直接把整个代码库丢给 LLM"和"让 LLM 生成静态分析规则"两种极端方案形成对比。

- **基于双向类型系统的形式化规则**（论文附录给出）：
  - 变量初始化：`Γ ⊢ x : τx`，其中 `τx = inf(nx)` 由自然语言上下文经 LLM 推断；
  - 操作推断：`τo = op(o, τe1, ..., τen)`，LLM 综合操作数与操作本身定义输出类型；
  - 赋值合并：`Γ(x) = unify(τx, τe)`，LLM 合并已有类型与新类型；
  - `inf`、`op`、`unify` 三个关键函数均由 LLM 实现。

- **PYSETYPE 实现流程（三阶段）**：
  1. **程序准备**：基于 pytype（Google 开源 Python 类型分析器）生成依赖接口存根（.pyi）、构建 CFG 与逐文件对象映射；识别 Flask/FastAPI/Django 的 Web 入口点与 `main` 函数。
  2. **SETYPE 推理**：按 CFG 以字节码级别模拟程序执行；对赋值、函数调用、分支、循环、合并等操作，向 LLM 发送小型提示（约 200 token），获取变量更新后的 SETYPE；循环采用归纳推理（迭代前类型 + 单次迭代后类型 + 迭代器类型）；捕获分支执行上下文。
  3. **漏洞发现**：针对外部函数调用，使用**基于清单（checklist）的验证策略**（如路径遍历规则包含三个独立检查项：是否访问路径、路径是否由外部客户端值构造、被调函数是否非自动净化函数）；用 taint 分析减少 LLM 查询次数；对 12 类常见 Web 漏洞（CWE-22/78/79/89/200/312/601/617/807/918 等）预定义规则。

## 6. 主要结论与发现

1. **SVEN 数据集上全面超越基线**：PYSETYPE 取得 87% 精度、87% 召回、88% 准确率、0.87 F1，四项指标均优于 CodeQL（0.67/0.39/0.83/0.49）、Bandit（0.75/0.84/0.70/0.79）和 Vulnhuntr（0.52/0.45/0.53/0.48）。

2. **在近期 CVE 上性能下降最小**：PYSETYPE 从 F1 0.87 降至 0.78，而 CodeQL 从 0.49 降至 0.33、Bandit 从 0.79 降至 0.46、Vulnhuntr 从 0.48 升至 0.53。这说明 LLM 语义推理能力对**未见漏洞模式具有泛化性**，而传统静态规则难以检测新漏洞模式。

3. **发现 15 个零日漏洞**（9 个路径遍历、5 个开放重定向、1 个 SQL 注入），9 个已获开发者确认；涉及微软官方库、PSF 服务器基础设施、IRS 维护的系统等高知名度代码库。

4. **基线工具对比**：15 个零日漏洞中，CodeQL 只能检出 9 个、Bandit 检出 2 个、Vulnhuntr 检出 1 个——传统工具漏报源于规则缺失，LLM 工具漏报源于幻觉与分析不完整。

5. **跨框架漏洞分布规律**：Django 中开放重定向更常见（"next"参数设计模式）；Flask 中路径遍历更常见（文件操作的灵活性）。

## 7. 优点与亮点

- **新颖的漏洞建模视角**：将漏洞视为语义类型不匹配，是一种对漏洞检测问题优雅的重构；类型系统框架提供了理论支撑（形式化规则完备）。
- **扬长避短的混合架构**：用确定性静态分析保证代码覆盖率，用 LLM 负责语义推理与弹性判断，避免了纯 LLM 的幻觉与纯静态规则的僵化。
- **防数据泄漏设计**：专门构造 LLM 知识截止之后的新 CVE 数据集，对结论的可信度至关重要。
- **实际成本可控**：$3.19 分析 26k 字节码的大项目，使工具具备真实部署的价值；与 Vulnhuntr 对比显示其虽然更慢但更深入、更系统。
- **LLM 查询设计精巧**：约 200 token 的小提示、每次只聚焦一个操作，降低不确定性；checklist 式验证分解复杂检查；taint 分析减少冗余查询。
- **可解释性较强**：SETYPE 类型轨迹和 LLM 推理链提供了发现漏洞的语义依据，优于纯机器学习方法的黑盒判断。

## 8. 不足与局限

- **静态分析固有盲区**：
  - 无法分析从入口点不可达的代码（如 Django 框架经多态调用的方法覆写、动态导入模块）；
  - Python 动态特性（运行时按配置文件导入模块）超出分析能力；
  - 依赖库与目标项目之间的隐性交互（如类继承回调）可能被遗漏。

- **LLM 推理的不稳定性**：
  - 产生误报（如将模板字符串误判为用户可控）与漏报（同一项目中 5 个相似 SQL 注入只检出 4 个，因 LLM 对 `db.query` 的判定不一致）；
  - 单次运行的随机性未系统评估（论文仅通过 `top_p=0.3` 缓解）。

- **跨语言交互缺失**：仅启发式处理 Python 与 HTML 模板等跨语言交互（如模板渲染 XSS），无法精确建模各语言的安全转义语义。

- **实现层面的限制**：
  - 仅支持 Python 3.10（字节码因版本而异）；
  - 仅支持 Flask/FastAPI/Django 三个 Web 框架；
  - 仅覆盖 12 类 CWE，远未覆盖全部常见漏洞类型；
  - 高级/动态特性（元类、复杂装饰器、动态导入）可能建模不准。

- **实验覆盖短板**：
  - 无消融实验，难以量化各组件（如 checklist、taint、执行上下文）的独立贡献；
  - 无不同 LLM 后端的对比实验；
  - 无跨 Python 版本评估；
  - 部分数据集较小（近期 CVE 仅 9 个），统计显著性有限。

- **效率瓶颈**：完整分析时间以分钟至小时计（对比传统工具秒级），虽成本可控但耗时仍是实际采用的门槛。
