## 摘要
新兴的智能体互联网使得由LLM驱动的智能体能够发现对等体、调用工具并跨组织边界委派任务。现有协议越来越多地定义了智能体如何交换消息，但并未定义智能体如何证明其身份、授权、所宣称的能力或委派后的问责性。我们提出InterSAGE，一套原生信任的协议套件，在通信协议之外提供了这一缺失的安全基础层，而非取代通信协议。InterSAGE包含四层：持久身份、发现、信任协商和问责。其四个核心原语是：(1) 将开发者、代码包、运营者和部署上下文绑定在一起的智能体身份卡；(2) 使用绑定DID的可验证凭据清单进行的能力感知发现；(3) 结合单调能力衰减与两级访问控制的信任协商；(4) 由内核中介的加密审计跟踪，无需共识账本即可将使用、委派和执行痕迹绑定到智能体身份。InterSAGE旨在补充MCP、A2A、ANP和AG-UI，使通信协议能够独立演进，同时保持信任语义的明确性、可移植性和可验证性。我们将InterSAGE与涵盖智能体协议、去中心化身份、OAuth/OIDC扩展、零信任治理、委派和审计架构在内的50多项工作进行了比较。我们表明，此前没有任何架构将持久身份、能力感知发现、信任协商和问责作为统一的四层信任基础层，共同用于安全的智能体互操作。

## Abstract
The emerging Internet of Agents enables LLM-powered agents to discover peers, invoke tools, and delegate tasks across organizational boundaries. Existing protocols increasingly define how agents exchange messages, but not how an agent proves its identity, authorization, advertised capabilities, or accountability after delegation. We present InterSAGE, a trust-native protocol suite that supplies this missing security substrate alongside, rather than in place of, communication protocols. InterSAGE comprises four layers: Persistent Identity, Discovery, Trust Negotiation, and Accountability. Its four core primitives are: (1) Agent Identity Cards that bind developer, code package, operator, and deployment context; (2) capability-aware discovery using DID-bound Verifiable Credential manifests; (3) trust negotiation combining monotonic capability attenuation with two-tier access control; and (4) kernel-mediated cryptographic audit trails that bind usage, delegation, and execution traces to agent identity without a consensus ledger. InterSAGE is designed to complement MCP, A2A, ANP, and AG-UI, allowing communication protocols to evolve independently while keeping trust semantics explicit, portable, and verifiable. We compare InterSAGE with more than 50 efforts spanning agent protocols, decentralized identity, OAuth/OIDC extensions, zero-trust governance, delegation, and audit architectures. We show that no prior architecture jointly enforces persistent identity, capability-aware discovery, trust negotiation, and accountability as a unified four-layer trust substrate for secure agent interoperability.

# InterSAGE：面向智能体互联网的安全可验证互操作协议——论文总结

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：LLM 驱动的智能体（Agent）正在快速走向大规模协作，形成“智能体互联网”（Internet of Agents, IoA）。业界已涌现大量通信协议，如 MCP（智能体-工具）、A2A（智能体-智能体）、ANP（智能体网络协议）、AG-UI（智能体-用户）等。
- **核心问题**：现有协议主要解决“智能体如何交换消息”，即**通信互操作**，但普遍缺乏**安全互操作**的信任基础——智能体如何证明“我是谁”“我被授权做什么”“我宣称的能力是否真实”“我执行过的动作能否被追溯与问责”。
- **威胁动机**：智能体具有委派授权、非确定性决策、动态编排等特点，传统的 TLS、OAuth/OIDC、X.509 等机制无法覆盖其身份多维绑定、能力衰减、委派链和端到端问责需求。作者总结出六类智能体特有威胁：T1 身份伪造、T2 能力越权、T3 委派滥用、T4 跨域信任断裂、T5 支付与用量欺诈、T6 动作否认。
- **整体含义**：作者主张，IoA 需要的是一个与通信协议并列（或嵌入其中）的**信任平面（trust plane）**，而不是在通信栈上打补丁。InterSAGE 即为此而设计：一套四层信任原生协议套件，补充现有通信协议缺失的信任语义，而非取代它们。

## 2. 提出的方法论：核心思想、关键技术细节

### 2.1 总体架构：四层信任协议套件

- **L0 持久身份（Persistent Identity）**：通过“智能体身份卡”（Agent Identity Card, AIC）提供持久、密码学绑定的智能体身份。
  - AIC 形式化定义：`AIC = Sign_GAR(DID_agent ∥ K_pub ∥ S_max)`
  - 其中 `DID_agent` 来自 `<developer, code_pkg, deploy_ctx>` 三元组派生的结构化标识符，`K_pub` 是智能体 Ed25519 公钥（对应私钥被内核保护），`S_max` 是能力边界（最大权限集）。
  - **四维身份绑定**：开发者、代码包、运营者、部署上下文（图 2）。每个维度由不同方控制、独立签名验证，避免单点降级。
  - 信任锚为**全球智能体注册处**（Global Agent Registry, GAR），类似 CA，但支持中心化、联邦、链式部署。
  - 私钥保护分三档：OS 文件隔离、OS 钥匙串（如 Keychain、DPAPI）、TEE 安全围圈（SGX、Nitro）。无论哪档，私钥均不离开内核信任边界。
  - 身份生命周期：签发、轮换、吊销（含级联吊销）。

- **L1 发现与语义互操作（Discovery & Semantic Interoperability）**：
  - **能力感知注册**：注册记录由智能体用私钥签名，包含能力列表、语义标签、端点、协议支持、以及签名技能/工具清单 VC。
  - **语义标签**：区分系统能力（闭环能力词汇）和语义标签（开放式领域词汇），语义标签不具授权能力，仅用于发现。
  - **能力感知发现**：支持注册表中介和点对点两种模式。任何发现结果都需验证 AIC 和清单 VC。
  - **可验证技能与工具清单（Skill/Tool Manifest VC）**：每个技能/工具都是 W3C VC 格式的签名凭据，`credentialSubject.id` 绑定智能体 DID，由分发者或工具提供者签发，可选 GAR 背书。
  - 发现时执行**四步验证**：供应链签名验证、主题绑定验证（VC 的 subject 与展示者 AIC 一致）、权限对齐（清单 `perms_required ⊆ S_max`）、新鲜度（未过期/吊销）。

- **L2 信任协商（Trust Negotiation）**：
  - **双向证明协议**（图 3）：两个智能体通过各自内核进行挑战-响应，互相验证 AIC，计算基础设施能力上界 `S_infra = S_A_max ∩ S_B_max`，再应用应用层策略得到最终会话能力 `S_session = S_policy ∩ S_infra`，生成共享密钥和带 TTL 的会话令牌。
  - **委派链**：父智能体可以签发子 AIC，要求 `S_child ⊆ S_parent_max`、深度受限、继承租户、有效期 ≤ 父身份有效期。具有单调衰减、租户隔离、深度限制、级联吊销、有效期封顶、防环等六项结构性属性。
  - **两级访问控制**：基础设施层（密码学强制）与应用层（声明式策略）分离，最终权限取交集。即使应用策略被错误配置，也不能扩大密码学边界。

- **L3 问责与经济（Accountability & Economics）**：
  - **Token 用量追踪**：用量记录绑定智能体 DID、会话 ID、委派链，由内核签名，支持成本上溯到根操作者。
  - **支付原语**：提供定价广告、支付协商、计量服务、结算框架封装，不指定结算通道（可与 AP2 互补）。
  - **动作问责**：每个动作生成 trace entry，字段含 `prev_hash` 形成哈希链，并用内核私钥签名。可实现不可否认性和防篡改。
  - 对比 BlockA2A：InterSAGE 不依赖区块链共识，用电内核签名哈希链，适用于边缘、气隙环境，也可选择将根哈希锚定到公开时间戳或分布式账本。

### 2.2 设计原则

- P1 信任作为绑定层，而非附加件（信任原语嵌入协议消息）。
- P2 与现有互联网层互补，不取代 TCP/IP/HTTP/MCP/A2A 等。
- P3 通用密码学原语，无基础设施锁定（GAR 可中心化/联邦/链式，签名用 Ed25519）。
- P4 默认拒绝、收敛于严格（权限只允许交集，单调衰减）。
- P5 结构性保证优于基于策略的保证（能力边界签名在凭据上，而非依赖运行时策略引擎）。

### 2.3 安全性分析（方法的一部分）

- 采用增强型 Dolev-Yao 网络敌手模型，加上 LLM 级妥协能力（控制应用逻辑、提示注入），但不攻破内核私钥。
- 假设：GAR 诚实、内核完整、密码学可靠。
- 在属性层面证明：身份完整性、能力限制、委派安全、发现完整性、问责性。通过安全比较表与 AgentMesh、AIP、BlockA2A 在失败场景下对比（表 6），论证 InterSAGE 的结构性保证在 PDP 误配置、运营者凭据泄露、子智能体越权、日志篡改等场景下仍成立或受限成立。

## 6. 主要结论与发现

1. **核心结论**：智能体互联网需要信任基板，而非又一个通信协议；通信互操作让智能体“能对话”，安全互操作让智能体“能行动”。
2. **InterSAGE 是首个将持久身份、能力感知发现、信任协商（单调衰减+两级访问控制）和问责统一为四层信任协议套件的架构**（对比表 7 的联合覆盖论证）。
3. 每个原语虽被部分先前工作独立 anticipate，但**联合强制**是 InterSAGE 独有的。
4. InterSAGE 可嵌入 MCP、A2A、ANP、AG-UI 等协议消息，无需修改通信协议线格式，通信协议可独立演进。
5. 通过将能力边界签名在凭据中（而非运行时策略），InterSAGE 在 PDP 误配置、运营者泄露、日志篡改等故障场景下提供**结构性安全保证**，优于 AgentMesh 等运行时策略方案。
6. 通过内核中介签名，可在无区块链的环境中实现不可否认和审计追踪，扩大了部署范围（云、边缘、气隙）。

## 7. 优点

- **清晰的设计原则**：P1-P5 明确，尤其“结构性保证优于策略保证”具有方法论价值。
- **四层分解合理**：从身份→发现→协商→问责逐层递进，每层职责单一，接口清晰。
- **兼容性强**：不取代现有协议，而是以“信任原语嵌入消息”的方式工作，与 MCP/A2A/ANP/AG-UI 互补。
- **部署灵活性**：GAR 可中心化/联邦/链式；互认证协议支持共址、远程中介、P2P 三种拓扑；私钥保护三档可调。
- **安全分析较细致**：属性化的安全论证、与主要对比系统的故障场景对比，展示了不同实现机制在失败情况下的行为差异。
- **相关工作对比系统化**：按六个聚簇组织，用统一模式（共享目标、分歧点、可观察后果）对比，增强了可信度。
- **考虑实际问题**：如身份生命周期、委派链的六项安全属性、发现时的四步验证、用量记账和支付原语。

## 8. 不足与局限

- **定位局限**：作者自我定位为“positioning paper”，缺少完整的协议规范级细节、形式化验证（TLA+/ProVerif）、性能基准、实现细节和对抗性评估。
- **信任锚问题**：GAR 是集中化（或联邦化）信任点，若 GAR 根密钥泄露或不可用，整个生态安全将崩溃；跨 GAR 联邦需要额外协议。
- **认知安全不在范围内**：协议无法阻止提示注入导致智能体滥用其已被授权的能力——这被明确划为 LLM 认知层问题。
- **隐私暴露风险**：默认互认证中，请求者的完整 AIC 属性都会暴露给响应方；作者提到可用 ZKP 选择性披露，但该扩展尚未设计。
- **采用启动问题**：存在网络效应，早期部署动力不足；虽提出先独立采用 L0 的分阶段路径，但实际拓展有待验证。

- **实验空白**：没有量化性能、可扩展性、可用性数据；不能证明协议在实际大规模场景下的资源开销和可操作性。
- **对比覆盖的偏差风险**：虽然对比了 50+ 工作，但“唯一性”论证可能受限于选项集合和时间点（截至 2026 年），未来可能出现类似或更优方案。
