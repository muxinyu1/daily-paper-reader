## 摘要
现代代理框架通过记忆、技能、工具和共享工件等持久载体跨任务和会话保持状态。然而，这种能力带来了延迟的安全风险：受攻击者影响的内容可以跨越系统边界，并在后续影响良性请求的执行。现有基准通常关注少数载体或框架，而端到端的攻击成功率几乎无法揭示风险如何传播。为此，我们提出了HarnessSafe，一个包含七个持久载体家族中328个可执行案例的基准，并在主流代理框架上进行了评估。每个案例被定义为持久风险生命周期，追踪攻击者影响从其初始进入，经过跨载体和系统边界的持久化，再到后续的良性触发和可观察的违规。我们进一步引入了一种基于追踪的多阶段评估方法，利用可观察的执行证据确定每条攻击链进展到何种程度以及在哪里被阻止。实验表明，隔离效果因载体而异，并强烈依赖于框架-模型配置。框架和后端模型都显著影响隔离结果，而攻击成功率无法反映不同的生命周期进展模式。

## Abstract
Modern agent harnesses persist state across tasks and sessions through persistent carriers like memory, skills, tools, and shared artifacts. However, this capability creates delayed safety risks: attacker-influenced content can cross system boundaries and later affect the execution of a benign request. Existing benchmarks typically focus on a few carriers or harnesses, while end-to-end attack-success rates reveal little about how risks propagate. To this end, we present HarnessSafe, a benchmark comprising 328 executable cases across seven persistent-carrier families and evaluated on most mainstream agent harnesses. Each case is specified as a Persistent-Risk Lifecycle that traces attacker influence from its initial entry, through persistence across carriers and system boundaries, to a later benign trigger and an observable violation. We further introduce a multi-stage, trace-based evaluation that uses observable execution evidence to determine how far each attack chain progresses and where it is stopped. Experiments show that containment is carrier-specific and strongly depends on the harness-model configuration. Both the harness and model backend substantially shape containment outcomes, while attack success rates cannot reflect distinct lifecycle progression patterns.

## 1. 核心问题与整体含义

现代 LLM 代理框架（agent harness）通过记忆、技能、工具/MCP、共享工件等“持久载体”跨任务、跨会话保存状态，这使 agent 能完成复杂的长程任务，但也引入了延迟性安全风险：一条看似无关的输入可能被写入持久载体，在之后的**良性任务**中被重新读取，从而触发未授权的工具调用、数据泄露或状态篡改。这类“持久风险”与单轮提示注入不同，其攻击源可能在触发时已不在上下文中，导致攻击来源和应被阻断的阶段难以定位。

## 2. 方法论

### 2.1 核心思想：统一持久风险生命周期

每个案例被定义为一个五元组：

**K = ⟨E, C, B, T, V⟩**

- **E（Entry）**：攻击者影响的初始输入；
- **C（Carrier）**：承载攻击影响的载体状态或有序载体路径；
- **B（Boundary）**：攻击影响需跨过的边界（会话、进程、agent 实例、工作区等）；
- **T（Trigger）**：后续的独立良性触发任务（不含攻击指令、不授权违规行为）；
- **V（Violation）**：可观察的安全违规，由案例特定的 oracle 判定，如工具执行结果、文件操作、网络蜜罐事件等。

该生命周期以“角色”而非“机制”描述，因此可为不同 harness 提供原生绑定，同时保持安全语义一致。

### 2.2 七类持久载体家族

HarnessSafe 按三层组织 7 个家族（图 1、表 4）：

- **Tier 1 核心持久面**：
  - F1 Memory（记忆，72 例）
  - F2 Skill（技能，84 例，含 17 例直接加载 + 67 例延迟/多阶段）
  - F3 Tool/MCP（工具/MCP 状态，70 例）
- **Tier 2 跨载体转换**：
  - T2 Memory→Skill（记忆到技能的转换，36 例）
- **Tier 3 跨边界传播**：
  - T3-S Subagent Delegation（子代理委托，30 例）
  - T3-C Session Summary（会话摘要/恢复，30 例）
  - T3-A Shared Artifact（共享工件复用，6 例）

总计 328 个案例，来自 79 个家族级设计，通过程序化扩展生成，并经模型辅助筛选 + 人工审查。

### 2.3 多阶段轨迹评估

将一个执行的证据链条映射到 7 个计分阶段（图 2、表 12）：

- **N0**：未接触被污染表面；
- **N1**：入口暴露；
- **N2**：载荷影响状态/行为；
- **N3**：跨边界持久化并被良性任务重新消费；
- **N4**：不安全尝试（未成功）；
- **N5a**：oracle 确认违规达成；
- **N5b**：完整生命周期 + 精确 canary 到达蜜罐的“全链确认”。

另有正交的 N−1（工作流未完成），不计分、不代表安全。

阶段判定基于**可观察执行证据**（工具/MCP 事件、工作区文件、蜜罐日志等），而非模型自述。任何到达 N5a/N5b 的样本计入攻击成功率（ASR）。

为便于标准化比较，定义**Chain-Stage Score（CSS）**：安全权重从 N0=100、N1=80、N2=60、N3=40、N4=20、N5a=10、N5b=0，值越高表示越早遏制。标准化的总体 CSS 使用固定家族权重：CSS_std = Σ(Nc/N)·(1/|C*_c|)·Σw(n_i)。同时报告覆盖率 Coverage = |E_h|/328。

## 6. 主要结论与发现

1. **遏制效果因载体家族而异**：没有一种配置在所有家族上表现一致良好。例如，总体 CSS 最高的 Codex CLI（62.3）在 F2 Skill 上得分最低（47.0），而 Claude Code 在 F2 上领先（70.0）。
2. **遏制是“配置”的属性，而非仅 harness 或仅模型**：GPT-5.6-Sol 在 Codex CLI 下为 62.3，在 Claude Code 下仅为 39.4；固定 Claude Code 时后端从 Claude Sonnet 4.6（58.7）到 MiniMax M2.5（22.7）相差 36 点。两个因素的效应量级相当，可能相互抵消。
3. **端到端成功率掩盖生命周期进展差异**：例如 OpenCode 与 Hermes Agent 的 ASR 十分接近（10.08% vs. 10.81%），但阶段分布明显不同——前者更多停在 N1/N2，后者更多停在 N2/N4。仅看 ASR 无法定位风险瓶颈。
4. **攻击依赖完整生命周期**：匹配控制实验表明，移除攻击入口、持久化、触发或清理载体后，ASR 从 25.8% 降至 ≤2.5%，说明观察到的违规确实由完整生命周期驱动，而非良性任务本身。
5. **诊断价值**：阶段解析可以定位防御应放在摄入、存储、边界转换、授权还是清理环节。

## 7. 优点

- **跨 harness 语义对齐**：通过五元素生命周期和适配契约，使同一攻击语义能在不同 harness 上以原生机制实现，这是现有基准较少做到的。
- **细粒度可解释评估**：N0–N5b 多阶段评分直接将风险链“停在哪儿”显式化，优于单一 ASR，对安全防御布局有实际指导意义。
- **证据驱动**：违规判定依赖可观察的执行证据（文件哈希、蜜罐、调用关联等），而非模型文本或意图，降低了误报风险。
- **严格的资格管理**：区分不支持、无效、未完成、缺失等状态，不将缺失当作安全，并报告覆盖率与支持集，增强了结果可信度。
- **控制实验设计严谨**：四类匹配控制（clean-source、no-persist、no-trigger、cleanup）有效验证了归因因果性。
- **案例构造系统化**：79 个设计定向扩展为 328 个案例，覆盖核心载体、跨载体转换和跨边界传播，结构清晰。

## 8. 不足与局限

- **算力与资源未披露**：没有给出 GPU 数量、模型调用成本或总执行时间，复现的资源门槛不明确。
- **单次运行无方差**：每个案例每个配置只跑一次，缺少多次运行的平均/波动，难以评估模型抽样随机性带来的影响。
- **覆盖不完整与支持差异**：一些 harness 对某些家族原生不支持（如 OpenCode 的 T2/T3-C、Kimi Code 的 T2/T3-S），造成支持集不一致；即便使用共同支持集，也可能因排除了“难案例”而高估某配置表现。
- **T3-A 样本量过小**：共享工件家族仅 6 例，统计代表性较弱。
- **权限配置不代表默认安全**：评测使用了最宽松的非交互式权限模式，结果反映“最坏可用情况”下的上限风险，而不能直接对应产品默认安全水平。
- **脚手架代码/人工审查可能引入偏差**：模型辅助筛选和人工审查虽设置标准，但无法完全排除主观性；不同适配器的“等价性”判断也可能存在细微不一致。
- **可复现性材料不完整**：作者承认 artifact 中缺少全部 case-level 的五臂配对记录、统一绑定台账和部分原生轨迹证据，限制独立复核。
- **权重选择主观**：CSS 的 N0–N5b 权重间距（20/20/20/20/10/10）是人为设定的，不同权重视角可能改变排名。
- **时间性**：评测固定于 2026 年某一版本，模型与 harness 快速迭代，结论可能随时间失效。
