## 摘要
自动驾驶车辆依赖于庞大的安全关键软件栈，其中攻击者输入可达的弱点可能影响转向、制动或其他控制决策。静态分析可以识别候选位置，但动态确认可利用性需要可执行测试工件，而这些工件难以手动构建。我们研究大语言模型（LLM）能否为开源自动驾驶栈Autoware自动化此过程。我们对185个包进行了编译器精确的静态分析，识别出1,375条决策规则、2,274项验证检查和482条输入到安全输出的流，据此推导出弱点分类体系，并抽样了740个可达位置。两个本地开放权重LLM、一个无静态上下文的消融模型和一个朴素模板基线生成了3,700个工件集，这些工件集在消毒器下针对真实构建进行编译，通过编译器在环反馈进行修复，并在可执行时进行模糊测试。主要结果是一个构建集成失败分类体系，显示80%的首次编译失败源于依赖连接而非程序逻辑。推理模型首次尝试编译了64%的测试工具，而代码专用模型仅为6%。仅通过大量打桩，推理模型的修复才实现了完整的对象可编译性；其测试工具中不到一半到达了模糊测试器，所有37次观察到的崩溃均源于被打桩的代码而非Autoware。在预算内没有候选弱点被动态确认。这些结果表明，构建集成（而非候选生成或模糊测试）是可靠地对完整自动驾驶软件栈进行LLM辅助动态分析的主要障碍。

## Abstract
Autonomous vehicles depend on large safety-critical software stacks, where weaknesses reachable from adversarial inputs may affect steering, braking, or other control decisions. Static analysis can identify candidate sites, but dynamically confirming exploitability requires executable test artifacts that are difficult to construct manually. We investigate whether large language models (LLMs) can automate this process for Autoware, an open-source autonomous-driving stack. We perform compiler-precise static analysis across 185 packages, identifying 1,375 decision rules, 2,274 validation checks, and 482 input-to-safety-output flows, from which we derive a weakness taxonomy and sample 740 reachable sites. Two local open-weight LLMs, a no-static-context ablation, and a naive-template baseline generate 3,700 artifact sets, which are compiled against the real build under sanitizers, repaired through compiler-in-the-loop feedback, and fuzzed when executable. The main result is a build-integration failure taxonomy showing that 80% of first-shot compilation failures arise from dependency wiring rather than program logic. The reasoning model compiled 64% of harnesses on the first attempt, compared with 6% for the code-specialized model. Repair achieved full object-compileability for the reasoning model only through extensive stubbing; fewer than half of its harnesses reached the fuzzer, and all 37 observed crashes originated in stubbed code rather than Autoware. No candidate weakness was dynamically confirmed within budget. These results show that build integration, not candidate generation or fuzzing, is the primary barrier to reliable LLM-assisted dynamic analysis of full autonomous-vehicle software stacks.

## 6. 主要结论与发现

- **没有候选弱点被动态确认**：在预算内，所有条件中无一弱点被确认为真实可利用。
- **首次编译失败主因是依赖接线**：80% 的首次编译失败（1,817/2,259）源于缺少 ROS/Autoware 头文件或源文件路径无效，而非程序逻辑错误。
- **模型差异显著**：
  - 推理模型（gpt-oss:20b）首次编译率为 64%（有上下文）和 24%（无上下文）；
  - 代码专用模型（codestral:22b）首次编译率仅 6%（有上下文）和 <1%（无上下文）。
- **静态上下文有效**：使推理模型首次编译率从 24.2% 提升至 63.9%，说明静态分析结果能实质改善工件质量。
- **修复导致“stub 收敛”**：编译器在环修复虽把推理模型的对象编译率提高到 100%，但这是以引入 stub、替换真实实现为代价；只有 289/740（有上下文）和 315/740（无上下文）的 harness 真实链接并到达模糊器。
- **全部 37 个崩溃均来自 stub 代码**，而非 Autoware 本身，因此都是假阳性。
- **核心结论**：构建集成（依赖解析、正确链接、真实目标可达）是 LLM 辅助动态分析在大型自动驾驶栈上的首要瓶颈；对象编译成功不能作为有效分析的代理指标。

## 7. 优点

- **首次端到端研究**：第一次在完整开源自动驾驶栈上，将仓库级静态分析、LLM 工件生成、原生构建集成、模糊测试与崩溃分诊集成为统一流水线。
- **系统性的失败定位**：不仅报告“失败”，而且通过故障分类学精确指出“在哪个环节、以什么模式失败”（依赖接线 > 逻辑），为后续研究指明了技术路线。
- **受控实验设计**：保持提示、上下文、编译环境、预算一致，进行双模型 + 消融 + 基线对比，能分离出模型能力、上下文信息、修复策略各自的影响。
- **强调“真实可达性”而非“名义编译”**：区分对象编译、链接、目标可达、确认四个层次，避免了误把编译成功当作有效测试。
- **可复现性**：作者将释放提示、生成工件、静态分析输出、执行日志，支持他人复现与扩展。
- **实际指导意义**：明确建议将后续自动化焦点放在构建集成（依赖解析、原生链接、目标验证）而不是提示工程或单纯编译修复。

## 8. 不足与局限

- **静态分析为启发式**：决策规则分类和包级流分析并非完全过程间、非污点精确的，可能高估或低估攻击面。
- **编译覆盖不完整**：只有具有编译命令的包才能进入编译器精确清单；大量包可能未被分析。
- **实验仅限 Autoware 和两个模型**：结论难以一般化到其他大型机器人/自动驾驶代码库或其他 LLM。
- **模糊预算未充分执行**：配置 600 秒/目标，实际仅执行 60 秒；由于大量 harness 无法链接，即使延长预算也影响甚微，但严格来说时间不足。
- **宽松的“可编译性”定义**：论文以“对象编译成功”而非“完整链接并执行”为指标，导致大量 stub 被算作成功；因此所有编译率、修复率都偏向乐观。
- **修复循环的局限**：仅 3 轮，且生成和修复使用同一模型；没有尝试“链接感知”的修复策略。
- **预训练数据污染风险**：Autoware 是公开项目，可能已出现在模型训练数据中，但即便如此成功率仍很低，说明问题不是简单的记忆性生成。
- **无物理车辆验证**：实验全部在软件在环中进行，不能外推到真实车辆的物理安全性。
- **动态确认的破产**：由于未到达真实目标，无法对 740 个候选点给出真正的“确认/证伪”判断，只能得出“无法在当前流程下自动化确认”的结论。
