## 摘要
AI编码智能体基准使用Chen等人(2021)的pass@k估计器对智能体进行排名，但当前的实现错误地应用了该估计器：它们将n设置为单次提交中的单元测试数量，而非独立尝试次数，从而将测试套件规模与尝试独立性混为一谈。我们诊断了这一操作化错误，通过反例证明其错误性，并提出了reliability@k，即正确应用的同一估计器，其中n = 每个(任务, 智能体)对的独立rollouts数量，c = 完全通过的rollouts数量。在一个合成的多rollout基准中，错误应用的指标使得报告得分绝对值虚高0.85-0.97（报告值为0.96-0.98，而修正后为0.00-0.12），且廉价的单rollout代理无法替代重复运行（Spearman ρ = 0.417）。鉴于功能正确性并不蕴含安全性的证据，我们进一步提出了安全调整的reliability@k，该指标仅计数既功能正确又无高危不安全模式的rollouts。在初步的实时API测试中（使用三个智能体），该调整在我们当前的扫描器和阈值下未改变任何排名，因此我们将其作为一个建议的补充视角，其决定性评估需要未来更高统计效力的运行。最后，一个初步的5任务SWE-bench Verified试点研究在真实代码库环境中观察到同样的核心问题：宏平均隐藏测试通过率为0.80，而严格任务解决率为0.20。

## Abstract
AI coding agent benchmarks rank agents with the Chen et al. (2021) pass@k estimator, but current implementations misapply it: they set n to the number of unit tests in a single submission rather than the number of independent rollout attempts, conflating test-suite size with attempt independence. We diagnose this operationalization error, prove it by counterexample, and propose reliability@k, the same estimator applied correctly, with n = independent rollouts and c = fully-passing rollouts per (task, agent) pair. In a synthetic multi-rollout benchmark, the misapplied metric inflates reported scores by 0.85-0.97 in absolute terms (0.96-0.98 reported vs. 0.00-0.12 corrected), and a cheap single-rollout proxy fails to substitute for repeated runs (Spearman $ρ= 0.417$). Motivated by evidence that functional correctness does not imply security safety, we additionally propose security-adjusted reliability@k, which counts only rollouts that are both functionally correct and free of high-severity insecure patterns. In an initial live-API test with three agents, the adjustment did not change any ranking under our current scanner and threshold, so we present it as a proposed complementary lens whose decisive evaluation requires better-powered future runs. Finally, a preliminary 5-task SWE-bench Verified pilot observes the same core concern in a real repository setting: macro-averaged hidden-test pass rate was 0.80 while strict task resolution was 0.20.

- **整体含义**：有缺陷的基准不仅歪曲性能，还会误导开发优先级和企业部署决策。论文旨在为智能体代码生成提供更可信的可靠性与安全评测框架。

## 2. 论文提出的方法论

### 2.1 核心思想
- 正确区分**完成式生成**与**智能体式生成**的本质差异：智能体的一次运行是一个多步骤循环（计划→工具调用→观察→迭代），成本高昂且不可廉价重复；生产环境用户更关心"单次认真尝试成功的概率"，而非"多次尝试至少一次成功"。
- 提出可靠性视角下的修正评测指标，并将安全性纳入考量。

### 2.2 reliability@k（修正指标）
- **正确操作化方式**：将 Chen et al. 的估计器中的 n 设为每个 (task, agent) 对的**独立 rollout 次数**，c 设为**完全通过（全测试通过）的 rollout 次数**。
- 公式维持原形式：

\[
\text{pass@}k = \mathbb{E}\left[1 - \frac{\binom{n-c}{k}}{\binom{n}{k}}\right]
\]

- 当 n = 独立 rollout 数、c = 完全通过的 rollout 数时，该公式即 `reliability@k`，衡量的是"k 次独立尝试中至少一次完全成功的概率"。

### 2.3 security_adjusted_reliability@k（安全调整版本）
- 仅统计**既功能正确、又通过启发式安全扫描**的 rollout。
- 安全扫描器检测 7 种高危模式：`eval()`、`exec()`、`os.system()`、`subprocess` + `shell=True`、`pickle.load()`、`yaml.load()`（无 Loader）、`__import__()`。
- 每个模式扣 1/7 分，安全分数 ∈ [0,1]；rollout 须安全分数 ≥ 0.80 才被计入安全调整可靠性。

### H2（确认）— 分数膨胀严重
- 错误的测试级 pass@5 与正确的 reliability@5 相比，平均虚高 **0.924**（范围 0.85–0.97），远超预设的 0.50 阈值。

- 本次合成实验中未发生排名反转（agent-x > claude-code > codex 保持稳定）。

### H3（确认）— 单 rollout 代理不足
- 代理指标 proxy = pass_rate × (1 − regression_rate) × tool_efficiency 与 reliability@5 的 Spearman ρ = **0.417**（p=0.0218），远低于预设的 0.70 阈值。
- 多轮独立 rollout 采集是评估可靠性的必要条件。

### H4（未确认）— 安全调整未改变排名

## 8. 不足与局限

- **合成数据主导**：H1–H3 基于人为构造的 rollout 分布，不能代表真实智能体在真实代码库上的表现；论文定位为方法论演示而非生产基准。
